# Requirements Analysis

Elicit, document, and validate software requirements with user stories and acceptance criteria.

## When to Use
- When starting a new feature or project
- When translating business needs into technical requirements
- When validating requirements for completeness and consistency
- When writing acceptance criteria for user stories

## Guidelines

### Elicitation
- Ask clarifying questions to uncover implicit requirements
- Identify stakeholders and their priorities
- Distinguish must-have from nice-to-have requirements
- Document assumptions and constraints explicitly

### User Stories
- Format: As a [role], I want [capability], so that [benefit]
- Keep stories small enough to complete in one sprint
- Include acceptance criteria in Given/When/Then format
- Link stories to business objectives for traceability

### Validation
- Check for completeness: are all scenarios covered?
- Check for consistency: do requirements contradict each other?
- Check for testability: can each requirement be verified?
- Check for feasibility: can the team implement this?

### Non-Functional Requirements
- Define performance targets (response time, throughput)
- Specify security requirements (authentication, encryption)
- Document scalability expectations
- Include accessibility and compliance requirements

## Best Practices
- Involve developers in requirements review
- Use prototypes to validate UI requirements
- Maintain a requirements traceability matrix
- Revisit requirements when scope changes
